# Reconciliation procedure

## Locate the playbook and resolve guidance

Use the developer-supplied checkout path or `AI_ENGINEERING_PLAYBOOK_ROOT`. Otherwise resolve the skill directory's real path and check the checkout two levels above it. Confirm the [standards index](../../../standards/README.md), [templates](../../../templates/README.md), and [registry](../../../registry/skills.yaml) are available and identify the source revision. Prefer a committed source for adopted content. If the selected files differ from that revision, obtain approval for an identifiable snapshot and record its content digests.

Use the registry's `applies_when`, `phases`, `required`, `dependencies`, `contract`, and `compatibility` fields. Treat a skill as required when its registered workflow or phase and trigger apply. Include dependencies of the project's selected workflows as well as bootstrap's immediate needs. Match the project's stack versions and inspect the actual installed distribution, `SKILL.md`, relevant companions, and any tooling or permissions the scoped use needs. Verify source and revision, and distinguish an installed revision from the registry's reviewed revision. Check the enabled skill inventory, including explicit-only skills in the active plugin or standalone installation. A package cache alone supplies no evidence of discoverability.

Record scoped reference-only guidance when the registry allows it. Open the approved prose and applicable resources at the verified source. Check side effects before executing any upstream instructions. An optional skill can be deferred in favour of applicable maintainer docs and project checks. A missing or incompatible required skill blocks the workflow that needs it until the dependency is verified or the developer approves a compatible change to the workflow. Registry approval covers scoped use. Installation, upgrades, and enabling executable dependencies each require approval.

For frontend projects, verify framework dependencies and versions in the affected package and apply the [frontend standard](../../../standards/frontend.md#external-guidance). Scope React guidance to React packages and the registered task triggers, including in mixed-stack repositories.

## Preserve and repair upstream configuration

Read the existing `## Agent skills` pointers in `AGENTS.md` or `CLAUDE.md`, their targets, configured tracker and labels, domain layout, glossaries, ADRs, and local spec or ticket files. Resolve paths from the current setup. Recognise legacy artifacts before proposing migrations. A glossary or ADR directory that upstream creates lazily is not itself a setup gap.

For a real gap, read the registered setup skill and its selected tracker, domain, and conditional triage templates from the compatible distribution. Matt Pocock v1.3.2 ships `setup-matt-pocock-skills` as an explicit-only entry point. If the host requires user invocation, ask the developer to invoke the discovered entry point for the agreed gap and resume reconciliation afterwards. Use upstream's discovery and draft checkpoints. Use existing valid values as input and apply the approved gap through a targeted merge. When the upstream workflow would overwrite valid configuration or also perform unapproved writes, preview and agree on the restricted application of its templates and contracts before editing. Recheck remote and label state before any separately approved action. A failed lookup is unresolved evidence.

Preserve upstream's agent block in its established file. Route Codex from root `AGENTS.md` using the project template. When upstream lives in `CLAUDE.md`, link the upstream block or its canonical targets from `AGENTS.md`. Preserve existing scoped instructions and fix shadowed routing only with approval.

## Materialise the approved setup

- Use the template index to pick applicable documents and the repository's canonical destinations. Fill prompts with actual project decisions, supporting evidence, and links. In existing projects document verified product capabilities and architecture, including meaningful module boundaries, data and known limitations. Mark uncertain facts and planned work explicitly. Use upstream domain formats for glossary and ADR work when applicable.
- Keep one project-local index for adopted standards and skill dependencies. Use an existing equivalent when available, otherwise use `docs/standards/playbook/README.md`. Materialise each approved reusable policy as a stable revision-pinned reference accessible to project readers or as a local snapshot if the source is unavailable to them. For snapshots, preserve the policy text and resolve cross-links to local or pinned targets, including the exception and approval instructions. Keep project decisions in their canonical docs and link to them from the index.
- Record the playbook source and exact revision or approved snapshot identity, with a link to the adopted registry where accessible. For each approved skill record its registry ID, source and revision, trigger and phase, required status, companion or tool dependencies, and verification or blocker status. Preserve the applicable registry contract and compatibility limits in the index when readers cannot reach the registry. Link guidance to the convention or workflow that uses it and record optional fallbacks and approved exceptions there. Keep upstream instructions at their source.
- Merge pointers into the existing agent guidance by change type. Link the project index, architecture and product documentation, domain and tracker configuration, and executable verification commands. Route collaborators to `$pair-implement` when the project uses pairing. Preserve the primary workflow and upstream artifacts.
- Reuse the project's checks and CI. For gaps, agree on checks supported by the stack and add or configure only the approved tooling or gates. Record commands, execution contexts, and required versus advisory checks. Use trusted hooks for local checks or supported tool controls where appropriate, and CI or branch protection for required merge checks when available and approved. Preserve existing permissions and hook trust. Markdown checkpoints require human review. Automated checks and tool controls enforce only the operations they actually cover.

## Verify and repeat

- Check the diff against the approved write list. Verify links and effective root and scoped agent guidance, plus the upstream tracker, domain and applicable label mappings. Test tracker access with an approved read. Confirm adopted standards and guidance resolve without relying on a personal absolute path.
- Verify the configured skills and companions in the target environment. Check Codex discovery in a fresh session or the host's skill listing, including explicit invocation availability for both playbook skills when selected. Report disabled or missing entries. Verify approved hooks are loaded and trusted before relying on them.
- Run the approved local commands and inspect CI gate configuration and available results. Report failures, unrun checks, and why. Verify that every required workflow dependency is ready or has a named blocker.
- Recompute the reconciliation using the same decisions, revision and observed state. Compare intended and actual content before each write. Skip matching files and entries, preserve unrelated sections, and avoid timestamps or duplicate blocks that create churn. If execution was partial, re-read actual state and apply only remaining approved gaps. Ask for fresh approval when drift changes the intended action.
