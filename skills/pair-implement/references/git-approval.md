# Git approval procedure

## Capture the review candidate

1. Record the worktree, branch, and parent `HEAD`. Inspect status, staged and unstaged diffs, and relevant untracked files. Identify approved paths or selected hunks. Include file additions, deletions, binary content, and mode changes where applicable. If ownership or hunk selection is uncertain, stop for the developer to identify the intended changes.
2. Use a temporary Git index (`GIT_INDEX_FILE` outside the worktree) seeded from the reviewed `HEAD` with `git read-tree HEAD`. Stage only the selected paths or apply the selected patch to this temporary index. Use full paths relative to the repo root and literal pathspecs. Stage new files in this index to include their full content and mode. For files containing unrelated edits, rely on explicit hunk selection. Leave the real index and worktree untouched.
3. Review `git diff --cached --binary --full-index --no-ext-diff --no-textconv --no-color HEAD` against the temporary index. Check that it contains the whole increment and only that increment. Record the tree ID from `git write-tree` against the same index. Discard the temporary index. Include the branch, parent SHA, candidate tree ID and proposed message in the checkpoint. Preserve any hunk selection needed to reconstruct the candidate in the conversation.

## Verify and commit

1. After commit approval, verify the same worktree, branch and parent SHA. Recreate the candidate from the current checkout using the same selection. Compare its tree ID to the approved ID. If any approved content has changed or the candidate cannot be reconstructed, return to **REVIEW** before staging.
2. Inspect configured commit hooks and the real index. If a hook can change staged content during commit, use the repository's supported non-mutating invocation or prepare its changes before review and confirm the hook leaves the reviewed tree intact. If a hook still makes it unsafe to commit the approved tree, stop. If the index is empty relative to `HEAD`, stage only the approved patch and verify the staged tree with `git write-tree`. If already staged exactly as approved, use that staged tree. Preserve unrelated staged changes. If they prevent safe isolation, end the turn with the specific conflict and request an isolated index or worktree arrangement. Use explicit staging and normal repository hooks.
3. Immediately before `git commit`, recheck the branch, parent SHA and index tree. Commit with the approved message using normal repository hooks. Verify the new commit's parent and tree match the approved IDs, and report its SHA. If hooks or concurrent changes interfere, inspect and report the new state. Return to **REVIEW** rather than retrying a commit with changed content, and leave recovery of any unexpected commit for explicit direction.
